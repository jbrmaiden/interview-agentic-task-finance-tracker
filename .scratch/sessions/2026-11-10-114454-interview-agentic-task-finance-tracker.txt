  Your "no" on Q9 changes the alert design. If an alert may only follow a
  transaction, the hourly sweep can't stay as a backstop: it has no transaction
  to react to, so it would email a budget that was set while already over. Round
  2 covers what depends on that change.

  ❓ Q1 - Which transaction changes can send an alert: After one of these
  changes, the app checks the user's budgets and emails any that are over and
  haven't been alerted this month:
  - (a) New transactions only: manual create, CSV import, or a receipt scan that
    creates a transaction.
  - (b) Any change that can add spending to a budget: everything in (a), plus
    editing a transaction's amount, date or category, re-categorising (a rule
    apply or AI categorise), and reassigning transactions when a category is
    deleted. Deleting a transaction never sends an alert.

  Here's the case that separates them. A user re-categorises five transactions
  into Groceries and pushes it to 1,200 of 1,000. Under (a) there's no email
  until their next new transaction.

  ➡️ (b). The user really did go over budget at that moment, and each of those
  changes is a transaction change rather than a budget change. Budget create and
  edit still never send an alert, as you decided in Q9.

  ---

  ❓ Q2 - Already over, then a new transaction: Following on from your Q9
  answer, take a budget created at 500 when 800 has already been spent. No email
  goes out at creation. Then the user adds a 10 PLN coffee. Should the coffee
  send the alert, since the budget is over and hasn't been alerted this month?

  ➡️ Yes. The rule becomes "a transaction change that leaves a budget over sends
  its alert if it hasn't sent one this month". It doesn't have to be the
  transaction that crossed the line. That needs no before/after snapshot, and it
  still caps alerts at one per month.

  ---

  ❓ Q3 - Drop the sweep and retry on the next transaction: Should we drop the
  hourly backstop? Instead, the check would run inside the transaction-change
  request. A failed send is logged but doesn't fail the change. An alert is
  marked as sent only after the email goes out, so a failure gets retried on the
  user's next transaction change.

  ➡️ Yes. It's the only design consistent with Q9. The cost is that if the email
  provider is down, the alert waits for the next transaction, and I think
  that's acceptable.

  ---

  ❓ Q4 - What the default currency is: On creation, which currency should the
  picker preselect?
  - (a) The app-wide default, PLN, which is what new accounts default to.
  - (b) The currency of the user's account with the most transactions, so PLN
    for most users and USD for someone whose main account is in USD.

  The picker would still list only currencies the user's accounts actually have.
  A user with no accounts couldn't create a budget, and would see an empty
  state saying "add an account first".

  ➡️ (b), falling back to PLN when it's a tie. If (a) is what you meant by "its
  default config", say so.

  ---

  ❓ Q5 - ADR for per-currency budgets: Budgets scoped to a currency, with no FX
  conversion, meets all three tests for an ADR:
  - It's hard to reverse: it's in the schema, the uniqueness rule and how the
    limit counts.
  - It would surprise a future reader, who might ask why Groceries can't simply

  That empties the frontier. Here's the full design to confirm.

  The budget itself
  - One budget per category per currency, so "Groceries PLN" and "Groceries USD"
    can both exist. You set the currency when you create the budget and can't
    change it afterwards. Edit changes only the limit, which must be greater
    than 0.
  - A budget can't be created until you have at least one account.
  - A budget covers its category and all subcategories. Moving a category under
    a new parent automatically changes what its budgets cover. Deleting a
    category, directly or through its parent, deletes its budgets.
  - A parent and its child can both have budgets. A transaction then counts
    toward both, and each budget is tracked separately.

  How spending is measured
  - Spending counts only money going out, in the budget's currency, and only
    from the transaction's own category. Receipt line items are ignored. Income
    and refunds never reduce it.
  - The month is the current UTC calendar month. A budget created mid-month
    still counts the whole month, and only the current month is shown.
  - A budget is over budget only when spending is strictly greater than the
    limit. Spending exactly equal to the limit shows "0 left".

  Alerts
  - Every check emails each budget that is over and hasn't been alerted this
    month. It doesn't matter how the budget got there: new spending, or a limit
    set below what's already spent.
  - Checks run after every transaction change except delete: create, import,
    receipt scan, edit, recategorise, and reassignment when a category is
    deleted. They also run after a budget is created or its limit changes. The
    existing hourly maintenance loop runs one as a backstop.
  - An alert counts as sent only once the email has actually gone out, so a
    failed send gets retried by the next check. Unverified users are skipped and
    keep their alert for later.
  - The email names the category, the limit, the spending and how far over it
    is, and links to /budgets. Logs never contain amounts.
  - Strictly one alert per budget per month. Raising the limit doesn't reset it.

  Plans and data rights
  - Free users get 3 budgets and Pro users unlimited. The 3 comes from
    BILLING_FREE_MAX_BUDGETS and is exposed as maxBudgets through
    getEntitlements.
  - The billing page shows "N of 3 budgets", and the Budgets page shows an
    upgrade hint when you hit the limit.
  - After a downgrade, every existing budget keeps working; only creating new
    ones is blocked.
  - Budgets and their alert records are included in the export zip, removed by
    account hard delete, and covered by the ownership checks.

  same session.
